# ジョブ管理・GUI起動失敗時のロック解放

2026-09-12、基準 `dabc302`。O01のローカル運用に対する修正。
全体テストの終了時に出ていた `.manager.lock` のResourceWarningと、
初期化に失敗したアプリケーションが作業領域を保持する問題を分けて確認した。

## 先行反例と受入条件

`test_gui_mode_tracking.py` の5件だけでも、合格後の終了時に同じ警告が出た。
クラス共有のJobManagerに終了処理がなく、テスト終了後も参照されていた。
クラスcleanupへcloseを登録し、作業領域の削除より先に実行する。

製品の独立した操作不変量は「起動に失敗した所有者はOSの作業領域ロックを解放する」。
例外のtracebackを保持したまま、別に開いたファイル記述から `flock(LOCK_EX|LOCK_NB)`
が成功することを検査する。オブジェクトの破棄や警告の抑制に依存しない。
正常稼働中の所有者がいる場合は、同じ検査と二つ目のJobManagerが拒否され続ける必要がある。

修正前の4テストは1 failure・4 errorで失敗した。壊れたjob.json、復旧書込失敗、
復旧中断、`.plot-cache` が既存ファイルの場合にロックが残り、ブラウザー起動失敗では
サーバーを閉じなかった。旧版の失敗ログは保持する。

## 修正した動作

- JobManagerのロック取得・既存ジョブ復旧が失敗または中断した場合、ロックを閉じて元の例外を返す。
- GUIのトークン生成は管理器の作成前に行う。キャッシュ準備・HTTPサーバー作成の失敗や中断でも管理器を閉じる。
- 起動表示・ブラウザー・サーバー実行を同じ終了処理で覆い、ソケットを閉じる処理が失敗しても管理器を閉じる。

壊れた保存状態を無視して起動したり、既存ファイルを置換したりしない。
復旧途中の先行ジョブで既に行われた `interrupted` 状態への更新を巻き戻す契約は追加しない。
利用者が直接作った正常なJobManagerのclose責任も従来どおり。FEM・場・RF・保存形式は不変。

## 検証

追加6件、既存Job管理・GUI追跡・RF探索の起動排他・保存完了の計29件が合格（1.443秒）。
`-W always::ResourceWarning` を付け、同じ警告の発生元を含む全29件の終了まで警告なし。
同じ作業領域の再起動、正常時の排他性、壊れた入力の保持、中断、ソケット終了例外も確認した。

実際の127.0.0.1 HTTPサーバーで6確認が合格。通常/平面画面、認証付きジョブ一覧、
実ポート競合後のロック解放、終了後の再起動、ブラウザー起動失敗後の実ソケットとロックの解放を確認した。
外部HTTPは0。検証サーバーはすべて終了し、実行前後の2製品ファイルhashは一致した。
補助スクリプトの初回は画面URLを `/planar` と誤記して404になったため、既存の `/planar.html` と
ジョブ一覧APIの契約へ修正し、新規出力先で再実行した。製品の経路は変更していない。

証拠は `out/job-startup-cleanup-20260912`。`warning-before.log` と `failures-before.log` が先行反例、
`related-final-2.log` が29件、`live-final/report.json` が実HTTPの記録。
直前の全体973件・独立数値検証は[厳密アフィン追跡](PLANAR_EXACT_AFFINE_TRACKING.md)の記録。
この非数値修正後に全体979件を再実行したという主張ではない。
新規外部資料・依存はなく、Python標準の終了処理と既存のPOSIXロック契約だけを使用した。
