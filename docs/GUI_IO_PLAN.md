## 1. 目的と判断基準

現在対応する物理・形状の範囲で、初心者が形状を作り、計算条件を設定し、
電磁場とRF量を確認・比較・保存できる汎用的な操作環境を提供する。
GUI・CLI・Pythonは共通の入力と計算機能を利用する。
当面の到達点は、既に扱ったKEK教育加速器セミナー資料の対象操作を容易に行えること。
対象資料・ページは [既存マイルストーン](MILESTONE_SEMINAR.md) に固定されている。

ユーザー指定の以下の原則を、機能・設計・検証の判断基準にする。

- **例題への作り込みを行わない。** 例題名、ファイル名、固定寸法、4/7というセル数で
  計算・描画・判定を分岐しない。例題は通常の入力データと受入fixtureとして扱う。
- **開発のための開発を行わない。** 追加機能・抽象化・依存導入は、操作性、再現性、
  数値の信頼性、保守性のどれをどう改善するかで判断する。
- 対象の操作を既存APIで実現できるなら再利用する。将来の可能性だけを理由に
  プラグイン基盤、別ソルバー、万能CAD、独自UIフレームワークを先行実装しない。
- 工数やテスト数を成果指標にしない。必要な重複解消は行うが、全スクリプトの統一や
  無関係なリファクタリングを本マイルストーンの条件にしない。
- 実装案を変える際は、必要性、代替案、ユーザーに生じる改善、検証結果を短く記録する。
  受入基準を緩める変更や必須範囲の削減は、黙って計画へ織り込まない。

- 自動周波数チューニング、一般的な交差・縮退mode tracking、新FEMバックエンド。
- 高次要素、角部ピーク電場の精度保証、測定との一致や実機設計の認証。
- クラウド、複数ユーザー、アカウント機能、全OSの実行形式配布。

## 4. 共通入力と保存の契約

### 4.1 入力と編集状態

既存Case v1/v2を計算入力の正本として維持する。GUIは同じstrict parserを通す。
表示はmm・MHz等を利用できるが、計算と保存の物理量はSIへ明示的に変換する。
半径と直径、座標(z,r)と内部(r,z)を区別する。未知キーや未対応条件を黙って無視しない。

編集用情報（繰り返し数、セル・端部寸法、表示単位、掃引定義）を必要とする場合は、
版付きのプロジェクト文書としてCaseから分ける。不要なデータベースは導入しない。
編集定義から展開した実際のCaseを計算ごとに保存し、入力の対応をhashで記録する。
編集定義と展開済みCaseの二重管理で不一致を見逃さない。展開は共通Python機能が担う。

既存case.jsonを直接開き、輪郭編集・計算・保存できることを必須にする。
元データにない「セル構造」を勝手に推定しない。通常の輪郭から開始できるようにする。
追加schemaの正確なキー・移行規則はG1で仕様化し、既存Caseの意味やhashを不用意に変えない。

### 4.2 計算・結果管理

GUI・CLI・Pythonは同じ展開、入力検査、実行、結果読込、掃引・収束処理を利用する。
GUI内でRF量を別実装しない。既存の直接Python APIとCLIは維持する。
新しいコマンド名やAPI名は実装時にINPUT_OUTPUT.mdへ確定仕様として記載する。

ジョブ状態は待機・実行中・完了・失敗・中止を区別する。
計算中でも画面操作と中止要求を受け付けられる実行方式にする。
段階名・経過時間を表示し、根拠のない進捗率や残り時間を出さない。
出力は毎回新規とし、完了状態は必要ファイルの保存・検査後に確定する。
中止・例外・ディスク障害・アプリ再起動後に部分出力を成功結果として扱わない。
失敗時のログを残し、新規実行先で再試行できる。途中の固有値計算の再開は必須にしない。

保存対象は、実入力、編集定義との対応、メッシュ条件、環境と実装版、規約、全モード結果、
場、プローブ設定、検証状態。図だけでなく数値をCSV等で出力する。
既存結果も開けるようにし、完了情報のない旧形式はその状態を明記して必要ファイルを検査する。
同じ保存結果を開くために再計算を要求しない。

## 5. 画面と操作

基本の導線は「新規/開く → 形状 → 計算条件 → 実行 → 結果/比較 → 保存」。
例題読込は任意の開始方法とし、空のプロジェクトからも同じ操作で作成できる。

| 領域 | 必須操作 |
|---|---|
| 形状 | 寸法フォーム、頂点・直線・段差・円弧の表編集、断面プレビュー、軸と境界の識別 |
| 繰り返し形状 | 対応輪郭のセル定義・繰り返し数・端部の指定、展開輪郭の確認。4/7セル固定にしない |
| 計算条件 | モード数、β、導電率、蓄積エネルギー、端面条件、メッシュ、鏡映の指定 |
| 実行 | 開始・中止・状態・ログ・新規出力先。編集後の条件と既存結果を混同しない |
| 結果 | モード選択、周波数/RF表、輪郭・メッシュ、電場等高線/矢印、磁場、プローブ |
| 比較 | 複数条件の表と図、掃引、細分変化、適用可能なバンドの分散・fit残差 |
| 保存 | 入力/プロジェクト保存と再読込、結果再表示、CSV・図・既存場形式の出力 |

通常項目と詳細設定を分けるが、計算に使う値・単位・規約は確認できるようにする。
「高精度」という保証のないプリセットを作らず、メッシュ設定の実値を保存・表示する。
既存の境界実長・角近傍細分・交差分割・円弧弦誤差は詳細設定から指定可能にする。
円弧に角近傍細分を指定するなどの未対応組合せは、理由と修正箇所を示して拒否する。
不正入力は該当欄を示し、入力内容を失わせない。キーボード操作、焦点表示、
色だけに頼らない状態表示、日本語の項目説明を受入に含める。
自由なマウス作図や3D回転表示は、これらの操作に必要だと実証されない限り後回しにする。

## 6. 科学的に誤解させない表示

- 周波数順の番号、同定された物理ラベル、ユーザー注釈を別々に保持する。
  half-endバンド同定は構成・セル位置の明示と実場検査を要求する。
  不成立やfull-end・非周期形状で、周波数順から位相名を補わない。
- 掃引は各条件の独立スペクトルを保存する。一般のモード追跡は未対応と表示し、
  同じ番号を同一物理モードとして無条件に線で結ばない。同定できたラベルのみ対応比較する。
- 収束確認は同一形状・条件で行い、円弧の形状近似とFEMメッシュの細分を分ける。
  対応付けが不確かなモードの収束は「判定不能」とし、合格にしない。
- 計算完了と数値検証PASSを分ける。周波数、場形状、RF積分、表面場を別に評価する。
  残差が小さいだけではメッシュ収束済みにしない。
- ピークphasor、入力領域の蓄積エネルギー、鏡映前後の領域と正規化を明示する。
  R/Qはaccelerator/circuitの両定義と式を確認できるようにする。
- Epk/BpkはP1推定値。鋭角、未収束、ゼロ近傍のVaccに伴う未定義比を区別する。
  見た目の平滑化でピーク値を変更しない。TTF・加速長の規約も保持する。

## 7. 技術選定と段階

評価対象は導入手順、形状編集、場の描画、キーボード操作、計算中の応答性、中止、
外部通信なしの動作、配布・ライセンス、既存描画資産の再利用。
実測環境、起動時間、操作応答、代表結果の描画時間・メモリを記録する。
QtやWeb依存は、必要性と代替案を記録した依存判断後にのみ追加する。
ブラウザー方式ならローカル接続に限定し、外部CDN等を要求しない。

### 8.2 検証と証拠

- G0で各受入IDに操作手順・期待結果を割り当て、実装段階で自動操作可能なものを検証する。
  静的画像やリンク確認だけで入力・実行・中止の成功を判定しない。
- 既存unittestを実行する。追加検査は単位変換、保存往復、幾何不変量、失敗状態、
  実際の操作などの破れやすい契約に集中し、実装をなぞるテストを増やさない。
- GUI/CLI/Pythonで展開したcanonical caseが一致することを検査する。
  同じ保存結果の表示は元数値と一致し、独立再計算の比較は既存物理許容差を用いる。
  固有ベクトルの符号・縮退を考慮し、ファイルのバイト一致を数値再計算へ要求しない。
- 数値変更時は独立の解析/物理不変量の失敗を先に示し、
  `OPENBLAS_NUM_THREADS=1 python scripts/validate.py --out out/validation-<unique-name>` を実行する。
  最終統合でも既存数値検証を行い、周波数とRFの差を別々に報告する。
- A1〜A4の数値基準は既存受入記録を維持する。周波数0.1%、RF量1%、
  正規化した軸場相対L2差1%を、それぞれ既存の対象・定義で適用する。
  形状近似、メッシュ細分、表面場は別検査とし、未収束を小さい残差で置き換えない。
- WineはGUIの実行依存にしない。比較する場合は参照入力・hash・規約・出典を確認する。
  過去に照合済みという記録と今回の照合を区別する。必要な参照がなければ該当検査は
  未検証として残す。検証に必要なNG結果は新規計算する。
- A5の幾何は解析面積、正半径、接続、境界タグ等を検査し、場とRFは細分変化を確認する。
  同定適用外を含む形状でも、計算・保存・通常の結果表示は可能であることを確認する。
- 出力先は毎回固有の新規ディレクトリ。受入レポートにID、入力、コマンド/操作、
  実装版、環境、期待値、実測値、判定、証拠パスを保存する。
  判定はPASS/FAIL/未検証を区別し、欠落・不正レポートをPASSにしない。
- G5は依存導入後のオフライン起動から保存再読込まで検証する。
  実行したOSとツール版を記録し、未実行OSやHosted CIを確認済みとしない。

## 9. 完了と進捗の管理

全体完了はG0〜G5、A1〜A8の必須条件が証拠付きで満たされ、導入・操作ガイドが揃った状態。
ユーザーによる操作感の確認内容と未評価部分は技術的受入と別に記録する。
実装があるだけ、画面が表示されるだけ、計画のチェック欄を埋めただけでは完了にしない。
必須検証の未実施を計画から削って達成扱いにしない。

進捗は本書に段階別状態と証拠へのリンクを追記し、詳細ログは別の受入記録へまとめる。
既存のセミナー受入履歴は上書きしない。計画作成はBACKLOGのG-PLANとして管理する。
現在の進捗は以下。完了した検査を全体受入へ拡大解釈しない。
